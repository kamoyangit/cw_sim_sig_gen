# cwsim — IONOS/Watterson HF チャネルを通したラベル付き CW

既知のテキストを **IONOS シミュレータが実装しているのと同じフェージングチャネルに通したモールス音**に変換し、サンプル精度の正解ラベルと一緒に出力するオフライン生成器。CW（モールス）復調器の訓練・評価データを作るために作られており、ボトルネックは計算量ではなくラベル付きデータである。

`src/HFSim_BFD_2_05/HFSim_BFD_2_05.ino`（IONOS HF/VHF Channel Simulator, © 2020 Amateur Radio Safety Foundation Inc., MIT）の DSP を抽出したもの。数学は意図的にそのまま残し、Teensy のリアルタイム処理系は持ち込んでいない。

## 現在の状態（最初に読むこと）

このファイルは作業の記録であり、後から撤回した結論も含む。**現在の正しい数値は以下**であり、これと食い違う記述はすべて歴史的経緯である：

| | median/mean | IQR | フラッタ |
|---|---|---|---|
| Rayleigh 理論値 | 0.939 | 6.83 dB | — |
| 実録音 40m `7.020153 MHz` | 0.970 ± 0.026 | 6.58 ± 0.46 dB | 0.98 Hz |
| 合成 MPP | 0.922 | 7.08 dB | 1.23 Hz |

実チャネルは Rayleigh であり、Watterson モデルはそれを再現する。以前の 2 つの主張は 10 ms 測定窓によるアーティファクトで、撤回済み：「実チャネルはモデルより安定している」「3 つの統計量を同時に満たすパラメータは存在しない」。Rayleigh の IQR は 6.83 dB であり、8.7 dB ではない。

以下で **superseded** と記した節は、同じ誤りを繰り返さないために残しているだけである。現在の使い方だけを知りたい場合は `HowToUse.md` を参照。

## ビルドと実行

```sh
make                      # build/gen_cw をビルド
make test                 # 49 件（チャネル 26 + 校正 23）
```

```sh
./build/gen_cw --text "CQ CQ DE JA1ABC K" \
  --channel MPP --paths 2 --snr 0 --wpm 20 \
  --out msg.wav --labels msg.json

./build/gen_cw --text-file corpus.txt --repeat 4 \
  --channel MPD --delays 0,15,35 --doppler 1.0 \
  --fade-depth 12 --fade 0.5 --offset 40 \
  --snr -3 --seed 42 --out hard.wav --labels hard.json
```

`--out` は 32-bit float WAV。フェージングが平均正規化レベルに利得を乗せるため、**ピークが 1.0 を超える**。float のまま扱うか下流で正規化すること。クリップさせてはいけない。

`--list-delay-presets` で遅延テーブルの一覧を表示する。

評価用のグリッドを丸ごと作るには `generate_dataset.sh` がある。5 チャネル × 3 速度 × 5 S:N（75 ファイル、約 19 分・2.2 GB）を走査し、出力ディレクトリに `README.md` を書いてグリッドの内容・命名規則・S:N の基準帯域を記録する。seed はパラメータの組から決まるので、グリッドを変更しても既存ファイルは無効にならない。

## 出力

`msg.json` はファイルごとに以下を持つ：

| フィールド | 意味 |
|---|---|
| `text` | 正確なメッセージ |
| `channel` | モード、パス数、Doppler 広がり、遅延、フェード、タップ更新率、平均電力利得、seed |
| `snr` | 要求／実測の音声帯 S:N、および 250 Hz・500 Hz フィルタ内の等価 S:N |
| `cw` | wpm、Farnsworth の要素速度、トーン、立ち上がり時間、ジッタ、ドリフト |
| `characters[]` | 文字ごとの `start`、`end`（WAV 内のサンプル番号）と `min_gain_db` |
| `symbols[]` | 要素ごと（`dit`、`dah`、`element_gap`、`char_gap`、`word_gap`）の `start`、`end` |

`min_gain_db` は失敗分析を可能にするラベルである。フェードで失われた文字は大きな負値を示し、雑音で失われた文字はそうならない。

定義は **その文字の区間内で最も弱い 10 ms の key-down RMS を、レンダリング全体の長期 key-down RMS に対する比で表したもの**で、測定は雑音を加える**前**の信号に対して行う。したがってこれはチャネルの性質であり、復調器の結果ではない。単一タップではなく合成後のマルチパス信号で計算している。独立な 2 本の Rayleigh パスを足すと個々よりずっと浅くなり、パス単位の値ではフェードを大きく過大評価してしまうからである。最悪の瞬間を報告するので、1 文字がヌルとピークにまたがれば、依然として強い負値を示すことがある。

## CW 向けの遅延プリセット

IONOS は CCIR F.520 の 0.5〜4 ms の遅延を持つが、これはデータモード向けに校正されている。20 wpm では dit が 60 ms なので、4 ms のエコーはシンボルの約 7% にすぎず、実質的に聞こえない。HF CW の「こもった」エコー音は **10〜100+ ms** の現象なので、このツールは `cw-short`、`cw-mid`、`cw-long`、`cw-roundworld` のプリセットも用意している。PC には音声遅延線の制約がないため、`--delays` は任意の値を受け付ける。

フェージングのその他の部分（複素ガウスタップ、Doppler 整形）は速度に依存しない。CCIR のパラメータが CW にとって誤った軸なのであって、モデルが不適切なのではない。

## S:N の基準 — 数値を引用する前に読むこと

`--snr` は **key-down 時の信号電力** 対 **`--bw` 内の全雑音電力** の比で、いずれもレンダリング全体で測る。雑音は連続、信号は断続である。

これが重要なのは、受信機が 3 kHz で聴いているわけではないからだ。同じ録音が `--snr 0` のとき、250 Hz フィルタ内では約 **+10.8 dB**、500 Hz では **+7.8 dB** になる。JSON は 3 つとも報告するので、帯域を書かずに結果を引用することはできない。

## IONOS ファームウェアからの意図的な逸脱

いずれも意図的である。重要な挙動はテストで固定している。

1. **IONOS の利得チェーンではなく電力正規化。** IONOS は信号と雑音を和が 1 になる利得で混合する（`g_s = R/(1+R)`、`g_n = 1/(1+R)`）。そのため表示される S:N は、入力音声が設計レベルにあるときだけ正確になる。マニュアルが入力レベルを特定の窓に固定しているのはこのためである。オフラインには依存すべき入力レベルが存在しないので、既定ではチャネルを長期電力利得 1 に正規化し、実測した信号電力から雑音を決める。`--hardware-staging` は元の絶対チェーン（4.28 dB の `AdjustS_N` 校正定数、3/6 kHz に対する 0.235/0.313 の固定雑音 rms を含む）を再現し、ハードウェアとの比較に使う。
2. **タップ利得の補間。** IONOS は `AudioMixer4` の利得を音声ブロックごとに 1 回更新するため、タップは Doppler の 64 倍のレートで 0 次ホールドされる。これにより利得が階段状になり、スペクトルにステップ状のアーティファクトが散らばる。ここでの既定は線形補間（Watterson の理想に近い）。`--interp zoh` でファームウェアの挙動を再現する。
3. **FIR のウォームアップ。** ファームウェアは 128 タップの遅延線が埋まるまで約 2 秒かけてフェードインする。オフラインではこれを捨てる（256 タックのプリロール）ので、冒頭の文字が深いフェードとして黙ってラベル付けされることがない。
4. **周波数領域での小数遅延。** ファームウェアはミリ秒単位の `AudioEffectDelay` を使うが、この実装はサンプル精度である。
5. **雑音。** ガウス性で生成し、理想的なマスクで帯域制限してから目標電力にスケールする。ファームウェアは一様白色源を 119 タップ FIR で低域通過させる。帯域内のスペクトル形状はどちらも平坦で、高次統計が異なる。
6. **フラットフェーディング** は dB で連続的に適用する。`--hardware-staging` では `Fade()` と同様に整数 dB に量子化する（包絡への `int()`）。

### 知っておく価値のある校正上の発見

IONOS のタップ生成器は `0.1 <= |z|^2 < 1` の環の外側のサンプルを棄却するため、Box-Muller の半径が切り詰められる。結果として得られる複素重みは、成分あたりの分散が理想的な複素ガウスより **1.28 dB 低い**（`E[|z|^2] = 1.4883`、本来は 2）。2 パス／4 パスの `fltSTD`（4.0 と 4.0/√2）はこの 2 ケースを厳密に等しくする。それがこの定数の存在理由であり、実際に保証されている。ただし絶対レベルは教科書的な Watterson モデルが与える値ではない。テストは 2 パスと 4 パスの比を検証し、報告される `mean_power_gain` は実値を反映する。

## テストが実際に検証していること

`make test` は生成器に対して 26 件のチェックを実行する。主なもの：

- **S:N の精度** −5〜+30 dB にわたり、レンダリングされた音声から独立に測定（雑音は要素間ギャップから、信号は key-down から雑音を引いて求める）。0.5 dB 以内。
- **フィルタ帯域幅の換算** `10·log10(BW_audio / BW_filter)` に対して。
- **Doppler のスケール不変性** — 128 タップのガウス FIR が広がりの 64 倍のレートで動くため、*正規化した*タップスペクトルは全 CCIR チャネルで同一でなければならない。フェージング生成器がファームウェアの設計に合っているかを見る、最も強い単一の検証である。
- **Rayleigh 包絡** スケール不変な分位点（`median/mean`、`q10/median`、`q90/median`）による。複素ガウスチャネルが作るべき分布である。
- **2 パスと 4 パスの平均電力の一致** 生の利得段を通して。
- **フラットフェードの深さ** 要求値に対して。
- **キーイングのタイミング** wpm からの dit・dah 長、およびメッセージ全体の単位ごとの一致。
- **`min_gain_db` とレンダリング音声の突き合わせ** 文字ごとの最弱 10 ms 窓を独立に再計算し、ラベルが黙ってずれないようにする。
- **ラベルと音声の整合**、seed ごとの決定性、seed への感度。

## 実録音に対するリアリズムの検証

`calibrate.py` は録音のチャネル統計を測るので、実キャプチャと合成を比較できる。`numpy` と `scipy` が必要。

```sh
python3 calibrate.py analyze real.wav          # これはどんなチャネルか
python3 calibrate.py compare real.wav synth.wav
python3 calibrate.py roundtrip                 # 推定器の閉ループ検証
```

`compare` は共通の指標を並べ、key-down 包絡の分布と瞬時周波数のフラッタに対して 2 標本 KS 検定を行う。

### I/Q 入力

使える。しかもこちらが優れている。録音は自動判別される：2 チャンネルがほぼ同一でないステレオ WAV、複素 `.npy`、生のインターリーブ `.cf32` / `.cs16` は I/Q として扱い、それ以外は音声経路に流す。`--iq` / `--mono` で強制できる。生フォーマットは `--fs` が必要。

```sh
python3 calibrate.py analyze sdr_capture.wav              # オフセットは自動検出
python3 calibrate.py analyze sdr.cf32 --fs 48000 --bw-hz 500
python3 calibrate.py compare sdr_capture.wav synth.wav --bw-hz 500
```

I/Q 経路は単なる便宜的なラッパーではない。複素ベースバンドではフェージング利得が推定ではなく**観測**できる。key-down 中は `|z|` がそのまま `|g(t)|`、`arg(z)` がそのままチャネルの位相であり、ヒルベルト変換を挟まない。帰結は 2 つ：

- フェード深さを 3 kHz の音声帯ではなく 500 Hz の通過帯で測るので、フェードの底に乗る雑音が減る。閉ループテストでは、I/Q 経路のほうが音声経路より真の深さに近い値を返した。
- `rayleigh_median_over_mean` が分布検定として意味を持つ（純 Rayleigh なら 0.939、フラットフェードが乗ると低下する）。

罠は帯域幅だけである。`snr_db` は入力が持つ帯域の内側で測られるので、音声ファイル（3 kHz）と I/Q ファイル（500 Hz）では通過帯だけで約 7.8 dB 違う。`compare` は入力種別が異なるときに注記を出し、フェード速度と duty は直接比較可能なまま残す。

**サイズ。** チャネライズはポリフェーズなので、数 MHz のキャプチャでも時間は問題ない（実測：2.4 MHz × 3 秒、7.2 Msample を 2.7 秒、オフセットは正確に復元）。制約はメモリで、キャプチャを全体読み込みするため、ピークで入力サンプルあたり約 64 バイトを見込む。**解析前に 192 kHz 以下へ間引くこと** — 500 Hz の CW チャネルにそれ以上は要らない。50 Msample を超えると警告を出す。

### 確立できたことと、できていないこと

**確立できた（閉ループ）。** すべての推定器は、真のパラメータを一切渡さない録音に対して検証されている。`make roundtrip` の現在の精度：

| 量 | 要求 | 測定 | 誤差 |
|---|---|---|---|
| S:N（フェージングなし） | 0 / 10 / 25 / 30 dB | +0.46 / +0.04 / −0.06 / −0.08 | < 0.5 dB |
| フェード速度 | 0.2 / 0.5 / 1.0 Hz | 0.20 / 0.50 / 1.01 | < 0.02 Hz |
| フェード下の S:N | 平均減衰から予測 | 0.1〜1.3 dB 以内 | — |

2 行目が最も重要である。フェード速度を 0.02 Hz で復元できるということは、包絡モデルとその測定が一致しているということであり、生成器が自分自身と一致しているだけではない。

**最初の実データ結果（n = 1）。** 7.025 MHz（40m CW）の 182 秒 MacSDR I/Q 録音を 7.0202 MHz 周辺 800 Hz でチャネライズし、それに合わせた合成録音と比較：

```sh
gen_cw --wpm 18 --channel MPG --snr 17.8 --bw 3000 --fade-depth 4 --fade 0.05 --seed 4
```

| 指標 | 実測 | 合成 | 差 |
|---|---|---|---|
| 800 Hz チャネル内の S:N | 18.760 dB | 18.880 dB | **+0.12 dB** |
| フェード速度 | 0.054 Hz | 0.054 Hz | **0.000 Hz** |
| 位相フラッタ（IQR） | 1.582 Hz | 1.528 Hz | **−0.054 Hz** |
| key-down 包絡 std | 4.42 dB | 4.76 dB | +0.34 dB |
| 包絡 IQR | — | — | 下の帯域幅表を参照 |
| 位相フラッタ分布 | — | — | KS D = 0.016 |
| 包絡分布 | — | — | KS D = 0.118 |
| duty | 0.595 | 0.509 | −0.086 |

S:N、フェード速度、フラッタ分布はよく一致している。duty が異なるのは、合成側のテキストが録音と違うためである。

**どの包絡統計が信頼できるか。** 唯一の clean なキャリア（7.0202 MHz）で帯域幅を掃引すると、自明に見える指標のいくつかがアーティファクトだと分かる：

| チャネル帯域 | dB std | IQR | p10–p90 | median/mean |
|---|---|---|---|---|
| 100 Hz | 9.39 | 10.5 | 26.2 | 0.948 |
| 200 Hz | 6.84 | 7.3 | 15.9 | 0.978 |
| 500 Hz | 4.98 | 6.4 | 12.4 | 0.964 |
| 800 Hz | 4.38 | 6.1 | 11.4 | 0.957 |

純 Rayleigh 包絡は **p10–p90 = 13.4 dB、IQR = 6.83 dB、median/mean = 0.939** である。ピーク包絡（p99）は帯域に依存しないが、フェードの底はノイズフロアで制限されるため、**p10–p90 と dB std は解析帯域とともに動き、チャネルのフィッティングには使えない**。median/mean は掃引全体で ±0.02、IQR は約 1 dB の安定性を持つ。この 2 つを使うこと。

これにより、このファイルの以前の結論も撤回される。あるキャプチャで 11.5 dB だった span を、受信機 AGC または Rician 成分の証拠と読んだ。同じ帯域の複数キャリアで span は帯域幅と信号品質だけの関数として 9〜26 dB に広がるので、その推論は支持されない。安定した統計で測ると、clean なキャリアの median/mean は **0.96〜0.98**、すなわち **実チャネルは Rayleigh であり、Watterson モデルの仮定どおり**である。AGC も Rician 項も説明に必要ない。

**確立できていない：一般性。** ある夜の 1 信号の 1 録音は分布ではない。正直に言える主張は *「ファームウェアと同一のタップ生成器を持つ Watterson/CCIR チャネルを、実 40m CW 録音の包絡統計に一致させた」* までで、*「実バンドと統計的に同一」* ではない。

実キャプチャ全般に当てはまる注意点が 1 つある。`--snr` は **フェードのピーク**で定義されるが、録音はフェードの掃引を平均する。`fade_average_penalty_db()` がその差を計算する（12 dB のフェードで約 −4 dB）ので、両者を正しく比較できる。

### ギャップを埋めるための録音手順

1. **既知のテキストを優先する。** ARRL/W1AW の符号練習送信は実 RF でコピー本文が公開されているので、同じファイルがチャネル校正と復調器の採点の両方に使える。7.000〜7.030 MHz 付近の WebSDR / KiwiSDR 録音は通常の QSO に使えるが、テキストは不明である。チャネル統計には十分で、CER には不十分。
2. **メタデータを記録する**：UTC の日時、周波数、受信機、フィルタ幅、AGC 設定、アンテナ。500 Hz フィルタ・AGC オンは、2.7 kHz・AGC オフとは別のファイルになる。
3. **最低 60 秒**、WAV、44.1 kHz、モノラル、非圧縮。ノイズリダクション、ノッチフィルタ、音声圧縮は有効にしない。目的はチャネルが何をしたかを測ることである。
4. **クリップを避ける。** クリップした録音は測定できない。
5. `analyze` を実行し、最も近い設定で候補を生成し、`compare` し、`--channel/--doppler/--fade-depth/--fade/--snr` を調整して繰り返す。`delta` 列が目的関数である。

ラベル付きの実オフエア音声として有用な公開ソースが 2 つある（ダウンロード可能なら）：ARRL W1AW の練習アーカイブ（実 RF、正確な転写）と Morse Learning Machine Challenge v2 の訓練セット（手作業でラベル付けされた雑音混じりの CW）。いずれもここでは再配布できないため、このリポジトリには同梱していない。

### 使えるキャリアの探し方（`scan`）

混んだバンドは測る前に探す必要があり、最も強いピークはたいてい誤った選択である。

```sh
python3 calibrate.py scan capture.wav --center-mhz 7.025 --bw-hz 200
```

`scan` は全キャリアを測定し、校正リファレンスとして 0〜110 点で採点する：dit:dah 比が 3.00 付近、duty が 0.40〜0.70、要素数が十分、S:N が適切、包絡の median/mean が Rayleigh の 0.939 付近、そしてチャネル幅を 2 倍にしたときのその比の安定性。減点の理由は数値だけでなく文章で報告する。

このツールが捕まえるよう作られている罠が 2 つあり、どちらもここで実時間を費やした：

- **強いピークは clean な信号ではない。** 40m の録音では、最も強いキャリアが 40〜90 Hz 隣に隣人を持つことが多く、どのフィルタ帯域でも分離できない。`in_channel_peak_ratio_db` がそれを直接測る。目的のキャリアから 15 dB 以内に競合ピークがあれば、その測定は `UNUSABLE` になる。それ以上狭めると、妨害を除く前にキーイングを壊してしまうからである。
- **キーイングの側波帯は独立したキャリアではない。** キャリアから 30〜40 Hz、約 −25 dB に立つので、全帯域のピークリストに現れる。純度判定をキャリアリストではなくチャネル内で測っているのはこのためである。

ここにある 2 つの 40m 録音で、`scan` は独立に `7.020153 MHz` を 182 秒ファイルで唯一の `clean` なキャリア（110 点）、`7.028153 MHz` を 73 秒ファイルで 83 点と判定した。手作業で見つけたのと同じ信号である。

31m の 3 録音（9.000 MHz、各 11〜16 秒）に適用すると、全キャリアを却下する。そして正しい。要素数 20〜56 ではフェージング分布の推定にはまったく足りず、チャネル内の `competing peak -8 dB` / `-0 dB` は、拾っているものが単一信号ではないことを意味する。**このコレクションで単一 Rayleigh チャネルの参照として生き残るキャリアは 7.020153 MHz だけである。** したがってここにあるすべてはサンプル数 1 に依存しており、内部整合性をどれだけ積んでもそれは変わらない。

### 1 本の録音でどこまで支えられるか

> **Superseded。** 下の IQR 列は 10 ms 窓で測ったもので、大きすぎる。修正値は後述の *推定器こそが問題だった* にある。

182 秒の MacSDR 録音を 6 つの独立した 30 秒区間に分けて個別に測定すると、測定が再現可能で、チャネルが 3 分間定常であることが分かる：

| 指標 | 平均 | sd | 最小 | 最大 |
|---|---|---|---|---|
| S:N | 24.42 dB | 0.60 | 23.62 | 25.42 |
| median/mean | 0.992 | 0.035 | 0.948 | 1.035 |
| 包絡 IQR | 7.28 dB | 0.41 | 6.57 | 7.77 |
| 位相フラッタ（IQR） | 0.982 Hz | 0.080 | 0.888 | 1.132 |
| dit:dah | 2.719 | 0.082 | 2.63 | 2.87 |
| duty | 0.683 | 0.012 | 0.668 | 0.698 |

つまり 1 つの*録音*から 6 つの使える推定値が得られ、それらは一致する。6 チャネルではないので一般的な主張の根拠にはならないが、推定器が雑音を出しているのではないこと、以下の数値がこの信号の安定した性質であることは示している。

ここでの 2 つの結果が生成器を変えた：

- **`dit:dah` は ITU の 3.00 ではなく 2.72** で、0.08 の安定性を持つ。実際のキーイングは正確ではないので、測定された習慣を再現するために `--dah-ratio` を用意した（既定 3.0）。ただし推定器自体が、フェージングに応じて 0.1〜0.3 低く読むことに注意。マスクの端が包絡とともに動くためである。
- **`--fade-depth` だけでは大きな IQR を再現できない。** これが、原因を伝搬ではなく HDSDR の録音系に向けさせた。

校正済みの候補（`--wpm 13.8 --dah-ratio 2.72 --channel MPG --snr 17 --fade-depth 2 --fade 0.05`）は S:N を 0.1 dB、フラッタを 0.1 Hz まで再現するが、**区間間のばらつきが実録音の 2〜3 倍**あった（median/mean の sd 0.112 対 0.035、IQR の sd 1.49 対 0.41）。実チャネルはモデルの予測より*安定している*ように読めた — しかし **その比較は不適切に選んだ合成ケースで行われており、撤回する**。MPP と正しい窓を使えばばらつきは一致する（sd 0.033 対 0.035、*推定器こそが問題だった* を参照）。

### Rician K：試したが、ギャップは埋まらなかった

> **Superseded。** この節は推定器が膨らませた IQR を追っている。`--rician-k` は今も実在する選択肢だが、必要ではなかった。*推定器こそが問題だった* を参照。

測定されたキャプチャは median/mean 0.992、IQR 7.28 dB で、Rayleigh の 0.939、6.83 dB と比較された。median/mean が Rayleigh より上なのは定常パスが作る挙動なので、`--rician-k` を追加した（K = 定常パス電力 / 散乱パス電力。平均電力の合計は 1 に保つので S:N の意味は変わらない）。180 秒信号で掃引すると：

| K | median/mean | IQR | フラッタ（IQR） |
|---|---|---|---|
| 0（Rayleigh） | 0.958 | 10.5 | 0.84 |
| 4 | **0.995** | 9.66 | 0.74 |
| 8 | 1.031 | 8.65 | 0.66 |
| 16 | 1.109 | 6.70 | 0.53 |
| **実録音** | **0.992** | **7.28** | **0.98** |

`K = 4` は median/mean をほぼ正確に再現し（0.995 対 0.992）、区間間のばらつきも一致する（sd 0.033 対 実測 0.035）。しかし**同じ K では IQR が 2.4 dB 広すぎ**、IQR 7.28 に届かせるには K を 12 前後にする必要があり、そこでは median/mean が 1.05 に振り切れている。フラッタはまったく逆方向で、K を上げると下がるのに、実信号は純 Rayleigh より*多く*のフラッタを持つ。

単一の K では 3 つ同時に合わない。`--rician-k` は実在する有用な自由度で、median/mean に対する正しいつまみだが、**測定されたチャネルは Rician チャネルではない**し、追加しても残差は説明できなかった。

**これにより、実チャネルが「モデルの予測より安定している」という以前の主張も撤回する。** それは不適切に選んだ合成ケース（MPG に `--fade-depth 2`）との比較から来ていた。MPP と正しい K を使えば区間間のばらつきは実録音と一致する（sd 0.033 対 0.035）。説明すべき余分な安定性は存在しない。

まだ合わないのは *狭い median/mean + 狭い IQR + 広い位相フラッタ* という組み合わせである。Watterson のどのパラメータ（Doppler、遅延、フェード深さ）も、Rician K も、その三つ組を作らない。単一の散乱パスと 1 本の定常パスより構造の多いモデルが必要で、たとえば強さの異なる 2 本の散乱パスを異なる Doppler シフトで重ねる構成だ。既存の生成器で試せるが、まだ試していない。

### 推定器こそが問題だった（修正済み）

フェージング統計を **10 ms** 窓で測っていた。これは要素内のリップルまでフェージングとして報告するのに十分短く、すべての包絡指標を膨らませていた。窓は現在 dit の半分で、8〜40 ms にクランプしている。

既知の Rayleigh チャネル上で、真のマスクに対して検証：

| マスク | 窓 | median/mean | IQR |
|---|---|---|---|
| oracle | 5 ms | 0.983 | 14.02 |
| oracle | 10 ms | 0.978 | 12.04 |
| oracle | 20 ms | 0.957 | 9.30 |
| **oracle** | **40 ms** | **0.922** | **6.89** |
| detected | 10 ms | 0.964 | 17.11 |
| detected | 40 ms | 0.964 | 9.20 |
| *Rayleigh 理論値* | — | *0.939* | *6.83* |

窓を修正すると、実録音と素の合成 Rayleigh チャネルは互いに、そして理論値と一致する（それぞれ 6 × 30 秒区間）：

| | median/mean | IQR | フラッタ |
|---|---|---|---|
| Rayleigh 理論値 | 0.939 | 6.83 dB | — |
| **実測 7.020153 MHz** | **0.970** | **6.58 dB** | 0.98 Hz |
| **合成 MPP** | **0.922** | **7.08 dB** | 1.23 Hz |

**つまり実チャネルは Rayleigh で、Watterson モデルはそれを再現しており、以前の「どのパラメータ組でも満たせない 3 つの統計量」は推定器のアーティファクトだった。** その結論と、それに基づく探索は撤回する：

- 包絡の説明に Rician K は不要。`--rician-k` は測定誤差の補正としてではなく、正真正銘のモデリング選択肢として残す。
- Nakagami-m は同じアーティファクトを追って追加されるはずだった。先に数値確認したところ、どのみち数値に合わない（m = 6 で median/mean 0.9926 だが IQR は 2.45 dB のみ）ので、実装しなかった。
- per-path Doppler は実在する能力なので残すが、データを合わせるのに必要ではなかった。

**私の 2 つの誤りをここに記録する**：Rayleigh の IQR は **6.83 dB** で 8.7 dB ではない（13.39 dB は p10–p90 の span）、そして推定器の窓は答えを数 dB 変えるパラメータである。

**key-down マスク：試して、そのままにした。** 真のマスクとの一致は IoU 0.665 にとどまり、これが oracle マスクに対して測定 IQR を 2〜3 dB 膨らませる（40 ms で 9.20 対 6.89）。改善の試み：

| 変更 | IoU | oracle 相当の包絡統計 | 実録音への影響 |
|---|---|---|---|
| ベースライン（パーセンタイル・ヒステリシス） | 0.665 | rayl 0.964, IQR 9.20 | 動作する |
| 零位相 `filtfilt`（約 15 ms の FIR 遅延を除去） | 0.676 | IQR 10.40 | 悪化 |
| 検出窓 10〜30 ms | 0.664–0.667 | — | 変化なし |
| Otsu 閾値 | 0.630 | IQR 8.6、ただし FN 10% | 悪化 |
| ピーク相対閾値 | 0.625 | **rayl 0.919, IQR 6.34** | **破綻：IQR 6.6 → 18.1、ratio 2.7 → 4.2** |

ここから分かった 2 つのこと：

- **IoU は誤った目的関数である。** ピーク相対の変種は IoU が*低い*のに、oracle のフェージング統計をほぼ正確に再現する。IoU を最適化していたら、誤った構成を選んでいた。
- **フェージングのピークは、実データではピーク相対閾値を破綻させる。** キャリアがフェードの深みにあるとき、「ピークから 12 dB 下」は雑音の中に落ち、マスクが分断され、要素長が雑音に崩れる。パーセンタイル版は動くピークに耐えるので、きれいな合成入力では測定上劣るにもかかわらず生き残る。

IoU 0.665 を超えるには、包絡を独立に閾値処理するのではなく、既知のモールス構造（要素長を単位長の k 倍に制約する）を使う手法が必要である。それはまだ試していない。

`dit:dah` も同じ理由で約 0.3 低く読める。

### per-path Doppler：フラッタは独立にできるが、IQR は動かない

> **Superseded。** これを動機づけた IQR のギャップは測定アーティファクトだった。`--path-doppler` は実在する能力である。*推定器こそが問題だった* を参照。

`--path-doppler` は各散乱パスに独自の Doppler 広がりを与えるので、あるパスはゆっくりフェードし（包絡が狭い）、別のパスは速くフラッタできる。これは素の Watterson モデルにはない自由度である。60 秒信号で実測の目標（median/mean 0.992、IQR 7.28、フラッタ 0.98 Hz）に対して測定すると：

| パス Doppler | median/mean | IQR | フラッタ |
|---|---|---|---|
| 0.5, 0.5 | 0.988 | 10.59 | 0.43 |
| 0.5, 4 | 0.931 | 10.75 | 2.06 |
| 0.5, 10 | 0.934 | 10.39 | 4.87 |
| 0.5, 25 | 0.953 | 9.72 | 11.18 |
| 1, 15 | 0.946 | 9.72 | 7.46 |
| **実録音** | **0.992** | **7.28** | **0.98** |

**追加した目的は果たしている**：位相フラッタが独立に調整できるようになり、2 本目のパスを変えるだけで 0.43〜11.2 Hz まで動く。単一の Doppler 値ではできなかったことだ。中間の設定で実測の 0.98 Hz に乗る。

**IQR は直らない。** パスの分割をどう変えても、包絡 IQR は 9.7〜10.8 dB にとどまり、実測の 7.28 dB に届かない。ここまでの探索で、議論ではなく測定によって排除されたもの：

| 試したもの | IQR への効果 | 判定 |
|---|---|---|
| フラットフェード深さ（0〜15 dB） | 最大 11 | 不足 |
| Doppler 広がり（1〜25 Hz） | 変化なし | 無効 |
| 遅延拡散（2〜140 ms） | 変化なし | 無効 |
| Rician K（0〜16） | 10.5 → 6.7、ただし median/mean が 1.11 へ | トレードオフが誤り |
| 異なる Doppler の 2 パス | 9.7〜10.8 | 無効 |

**狭い median/mean、狭い IQR、広いフラッタを同時に持つ**測定チャネルは、これらの組み合わせでは表現できない。Rician K が最も近く、トレードオフで失敗する。これはスケールではなく分布の*形状*を指している。Nakagami-m や対数正規の包絡なら IQR を median と独立に設定できるが、Rician と Rayleigh にはできない。次に試す価値があるのはそれで、タップ生成器への小さな変更で済む。

### HDSDR の録音が明らかにしたこと（と、そうでなかったこと）

同梱フォルダの 2012〜2017 年の HDSDR 録音は、いずれも包絡 IQR が 12〜28 dB で、Rayleigh の 6.83 dB と大きく違う。その差を追い、1 つずつ排除した：

| 仮説 | 検証 | 結果 |
|---|---|---|
| 受信機 AGC がフェードを圧縮 | AGC は分布を狭めるが、これは*広い* | 方向が逆 |
| フラットフェーディング / QSB | `--fade-depth` を 0→14 dB 掃引 | IQR は 11.1 dB までしか行かない |
| 速いフェージング | `--doppler` を 1→25 Hz 掃引 | IQR は 7.5〜8.4 dB のまま |
| 周波数選択性フェージング | `--delays 0,20,45` と `0,60,140` ms | IQR 8〜10 dB、広がらず |
| 帯域内の競合キャリア | 帯域掃引、`in_channel_peak_ratio_db` | clean も不良も*どちらも* −20 dB で、識別できない |

合成した単一 Rayleigh チャネルは、**モデルが持つどのパラメータを振っても IQR 7〜11 dB** に収まる。clean な MacSDR キャリアは 100 / 200 / 300 Hz で 10.5 / 7.3 / 6.8 dB を測り、モデルと一致する。HDSDR のキャリアは 26.9 / 23.0 / 13.1 dB で、モデルが作れる何とも一致しない。

したがって結論は「HDSDR の信号が少しずれている」ではない。**それらの録音はこのチャネルモデルではまったく再現できない**のであり、原因は伝搬ではなく HDSDR の録音系にある（AGC ではない。それは逆方向になる。ノイズリダクション、ノッチフィルタ、過載が候補として残る）。チャネルの参照には使うべきでない。MacSDR の録音は使える。

`envelope_db_iqr > 16 dB` がキャリアを利用不可と判定するようになったのも、これが理由である。「これは 1 つの Rayleigh チャネルか」を見るために利用できる最も鋭い検定で、median/mean も帯域内ピーク比も見逃す汚染を捕まえる。

### 良い録音が見つかったときのワークフロー

```sh
# 1. この中に使えるキャリアはあるか
python3 calibrate.py scan capture.wav --center-mhz 7.025
#    -> スコアが高く "clean" のオフセットを選ぶ

# 2. きちんと測定して出発点を得る
python3 calibrate.py fit capture.wav --offset-hz -4847 --bw-hz 200

# 3. 提案されたコマンドで生成し、比較して詰める
./build/gen_cw <fit が印字したコマンド> --out match.wav --labels match.json
python3 calibrate.py compare capture.wav match.wav --iq --offset-hz -4847 --bw-hz 200
```

`fit` は 6 区間を測定し、全統計量の平均とばらつきを報告して、出発点となる `gen_cw` のコマンドを印字する。参照キャプチャでは初回で median/mean が 0.006 以内、フラッタが 0.08 Hz 以内に入る：

| 指標 | 実測 | `fit` の提案 | 差 |
|---|---|---|---|
| median/mean | 0.960 | 0.954 | −0.006 |
| 位相フラッタ | 0.972 Hz | 1.054 Hz | +0.08 Hz |
| 包絡 IQR | 6.67 dB | 7.23 dB | +0.56 dB |
| S:N | 24.61 dB | 25.48 dB | +0.87 dB |
| フェード速度 | 0.072 Hz | 0.310 Hz | +0.24 Hz |

後のものが前のものにほとんど影響しないので、この順で調整する：

1. **`--snr`** — S:N の差が約 1 dB を下回るまで。S:N を大きく動かせる唯一のパラメータで、`fit` の推定が最も不確かな項目でもある（実測の 3 kHz→200 Hz 補正 7.5 dB を使っており、これは経験値）。
2. **`--channel` / `--doppler`** — フラッタと median/mean が合うまで。Doppler はフラッタを直接動かす。
3. **`--fade-depth`** — IQR が不足している場合のみ。`fit` が 0 のままにするのは意図的で、フラットフェードとマルチパスフェードは包絡だけからは分離できないため、早く入れると別のアーティファクトでアーティファクトを合わせることになる。
4. **`--dah-ratio`** — 最後。送信者が正確だったと信じる場合のみ。`fit` は*測定された*比を再現するが、推定器は約 0.3 低く読む。

録音が使えると分かったときは 2 つを記録する：**メタデータ**（UTC、周波数、受信機、フィルタ幅、AGC とノイズリダクションの設定）と**区間間のばらつき**。区間間の散らばりが大きい録音は、平均がどれだけ良く見えても厳密な主張を支えられない。

### 実録音からの実務的な注意

- 夜間の 40m CW 帯は混んでいる。「最も強いピーク」で最初に選んだキャリアは、60 Hz 以内に 5 本のキャリアを持っていた。`--bw-hz` は 1 つの信号を分離できるだけ狭く、かつキーイング包絡を歪めないだけ広くする必要がある。ここでは 500〜800 Hz が機能した。
- `--bw-hz` は今は本当に効く（以前のリビジョンでは効いていなかった — バグ）。テストの掃引を健全性チェックに使うこと。チャネルを広げると S:N が下がり、測定されるフェード深さが浅くなるはずである。
- dit:dah 比が 3 から大きく外れる信号は、たいてい 1 つの信号ではない。統計を信じる前にキャリア数を確認すること。

## 見つけて修正したバグ：WGN が黙って MPP になっていた

`--channel WGN --delays 0,2` が `--channel MPP` とまったく同じチャネルを生成していた（Doppler 1 Hz、tick 64 Hz）。原因は処理順で、`--delays` が `paths` を 2 に上げ、その後の汎用的な「マルチパスには Doppler 広がりが必要」という補正が WGN を含む全モードで発火していた。結果として、遅延を与えた途端に WGN というフェージングなしのモードへ到達できなくなっていた。

フェージング系モードにのみ Doppler を発明するよう修正した。`--channel WGN --delays 0,2` は現在**静的マルチパス**である — 0 と 2 ms の定利得 2 経路で、これはくし形フィルタであり、求めるのは正当なことである。`--channel WGN --path-doppler 0.2,3` は明示的な要求なので、従来どおりフェージングする。

同じ修正で 2 つ目の不整合も直した。`--path-doppler` 使用時、ラベルの `doppler_spread_hz` はパスそのものではなく `paths` から導かれた値を報告していた。現在はパス 0 を反映し、全ベクトルは `path_doppler_hz` に入る。

どちらも回帰テストで固定している。

### オプション相互作用の全数監査

WGN/MPP の衝突を受けて、全モード・全オプションの組み合わせを掃引した。同じ一族の問題がさらに 5 つ見つかった。すべて、黙って受け付けられ、何もせず（あるいは落ちる）というものだった。

| 組み合わせ | 修正前 | 現在 |
|---|---|---|
| `--channel WGN --doppler 1` | **未捕捉例外でプロセス中断** | エラー、exit 2 |
| `--channel MPP --doppler 0` | 1 Hz に戻される | 尊重（静的マルチパス） |
| `--channel WGN --rician-k 4` | ラベルは 4、実際は未適用 | 警告、ラベルは 0 に訂正 |
| `--channel WGN --fade-depth 10` | ラベルは 10、実際は未適用 | 警告、ラベルは 0 に訂正 |
| `--channel WGN --paths 4` | 黙って無視 | 警告 |

最悪だったのは中断である。`--doppler` が `paths` を 2 に上げる一方で遅延リストを伸ばさないため、`Renderer` のコンストラクタが例外を投げていた。現在は報告するようになり、加えてコンストラクタを包んだので、将来別の不整合が生じてもプロセスを終了させない。

オプション処理はパース後・レンダリング前に一度だけ検証され、警告はラベルではなく stderr に出す。適用した原則は：**使われない値は、使われたかのように報告してはならない。**
